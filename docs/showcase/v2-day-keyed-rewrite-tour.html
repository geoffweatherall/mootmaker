The Day-Keyed Rewrite

Meetings used to be rows. Now a whole calendar day is one item — one DynamoDB write, one cache entity, one unit of retention, one thing to broadcast. This is a tour of that change for people who know the old codebase, with the testing weighted exactly as heavily as the implementation.

01 · Orientation

What actually moved

The old model stored one item per meeting and reached them through secondary indexes. The new model stores one item per calendar day and reaches everything by primary key. That single change is what unlocks the rest: a primary-key read can be a ConsistentRead, which removes the read-after-write bug class outright.

WasIsWhy it matters
One item per meeting One item per day, DAY#2026-09-14 Buys ConsistentRead; costs write amplification and contention
Four root fields, four Lambda invocations workspace(dates:) — one One request, one invocation, one SnapStart restore per page load
Two meetings GSIs, meeting-participants, cognitoSub-index All deleted Nothing is stored twice anywhere after this
myPerson then meetings — a waterfall A custom:personId claim on the token Zero lookups to know who you are
Unbounded growth 217 day items, hard cap 180-day horizon plus ~37 days retention — a row count, not a growth rate
Refetch on navigation Broadcast invalidations over a WebSocket Another user's booking appears without a refresh

Four workarounds were deleted, not fixed

Worth dwelling on, because it is the most transferable idea here. Each of these existed to paper over a race that the old shape made possible:

  • A router-state handoff carrying a freshly created meeting between two pages, plus its paired merge on arrival. It existed because reads went through a GSI, and DynamoDB refuses ConsistentRead on an index.
  • Two cache.updateQuery merges, because a read could lose a race with the write that preceded it.
  • Three pages firing two independent queries that settled at different times, so the screen assembled itself in visible stages.

The best fix for a workaround is a shape that cannot have the problem.

02 · Slice one

Resolvers that fetch only what was asked for

AppSync tells a direct-Lambda resolver which fields the client selected, as info.selectionSetList — a flat list of /-separated paths. So attendees { id } can do no Person lookup at all, while attendees { id name } does exactly one.

The first surprise cost an afternoon and is not in the AWS documentation: selectionSetList is not serialised by $util.toJson($ctx). The request template has to name it explicitly, which is why it went from a pass-through one-liner to a written-out heredoc. 

{
  "version": "2018-05-29",
  "operation": "Invoke",
  "payload": {
    "info": {
      "fieldName": $util.toJson($ctx.info.fieldName),
      "parentTypeName": $util.toJson($ctx.info.parentTypeName),
      "selectionSetList": $util.toJson($ctx.info.selectionSetList)  // ← or it is absent
    },
    "arguments": $util.toJson($ctx.arguments)
  }
}

The alias trap

An aliased field appears in the selection set only under its alias. Ask for roomName: name and you get room/roomName, never room/name.

Silent · 1

Enumerate the fields you consider expensive, miss an alias, and you return a stub. GraphQL then nulls a non-null field, and the null cascades up through the list to the whole meeting. Not a degraded response — missing data, with a 200.

So the test is inverted. Rather than asking "does the client want anything expensive?", the code asks "is everything selected known to be free?" — and anything unrecognised means fetch. Failure lands on the side of doing unnecessary work instead of losing data. 

private static final Set<String> FREE_FIELDS = Set.of("id", "__typename");

boolean needsLookup(final String prefix) {
    if (paths.isEmpty()) return true;          // no information → assume the worst
    final String nested = prefix + "/";
    for (final String path : paths) {
        if (path.startsWith(nested)
                && !FREE_FIELDS.contains(path.substring(nested.length()))) return true;
    }
    return false;
}

__typename has to be in the free set. Apollo adds it to every selection automatically, so without it the optimisation never fires for a single real client.

Why this needs two test layers

SelectionSetTest is driven by recorded payload shapes rather than end-to-end queries, because the cases that matter — an alias, a fragment, a missing key — are the ones an end-to-end test is least likely to hit by luck. But the alias case also has a deployed acceptance test, because its failure mode is GraphQL's non-null enforcement, which only exists inside a real executor. The unit test proves the logic; the acceptance test proves the consequence.

03 · Slice two

One item per day, and the locking that follows

The old model was lock-free by construction: independent per-meeting writes could not collide. The new model rewrites the whole day item to add one meeting, so two people booking the same date genuinely contend. Optimistic locking is new to this codebase.

The shape of the repository method is the design, not a style preference: 

public Day mutate(final String date, final UnaryOperator<Day> change)

It takes a function, so on a version conflict the change is re-applied against freshly read state. That is what makes a retry mean anything: "is this day full?" gets answered about the day as it is now, not as it was when the request arrived.

The first write is a different condition

Version 0 means "no item yet", so the condition is attribute_not_exists(pk) rather than version = 0. Two racing first-writes would both pass a comparison against an attribute neither of them can see.

Validation splits in two, and where each half runs is the point

  • Rules about the request — times, existence, capacity, lengths, the booking window — are checked once, up front.
  • Rules about the state of the day — is the room still free, is the day now full — are checked inside the read-modify-write.

This is what avoids the classic overbooking bug: two requests read a day holding 319 meetings, both conclude there is room, both write. The conditional write makes one of them retry — and re-running the day-state rules is what makes that retry correct rather than merely late.

One consequence rippled outward pleasingly. RoomAvailability had to stop touching DynamoDB, because a check that issues its own query cannot sit inside a retry loop. It became a pure function over a list — which is also what allowed the roomId-startTime GSI to be deleted. One change, three benefits.

A test double that can fail the way production fails

Silent · 2

FakeDynamoDbClient keyed on id and ignored condition expressions entirely. Every optimistic-locking test written against it would have passed vacuously — green tests over completely broken retry logic.

The fix went into that fake rather than beside it, which matters more than it sounds. A second, day-specific double would have left the original still lying to every other test that uses it. Instead it now keys on whichever partition key an item actually carries — pk for the meetings table, id for the others: 

final String keyName = item.containsKey("pk") ? "pk" : "id";

and it honours the two conditions DayRepository actually issues (attribute_not_exists(pk) for a first write, version = :expected for every later one), throwing on anything else: 

throw new UnsupportedOperationException(
    "FakeDynamoDbClient does not model the condition: " + condition);

That last line is the part worth copying. A fake that silently accepts an unmodelled condition goes back to passing vacuously the moment someone adds a third one; a fake that throws makes the next unmodelled condition a failing test rather than a quiet lie. It also checks every condition before applying any write, mirroring real transaction semantics: checking as it goes would let a later failure leave earlier writes applied, which is exactly the behaviour these tests exist to disprove.

An assertion that fails the deploy, not a booking

SnapStart executes a function's init when a version is published. So an invariant asserted in a constructor that runs at init is checked at deploy time. Raise a limit without redoing the arithmetic and the deploy fails — rather than a user's booking failing six weeks later.

This is also the tour's one piece of genuinely new Java. ResolverDispatchHandler runs the assertion before delegating to another constructor, which was a compile error before Java 22 and is finalised in Java 25 (JEP 513): 

public ResolverDispatchHandler() {
    Limits.assertConsistent();       // ← a statement BEFORE this(...)

    this(Map.ofEntries(
            Map.entry("Query.workspace", new WorkspaceHandler()),
            Map.entry("Query.meeting",   new MeetingByIdHandler()),
            // ... every field, constructed eagerly so INIT exercises them all
            Map.entry("Mutation.deleteMyAccount", new DeleteMyAccountHandler())));
}

Where you put an assertion changes what it protects.

Testing that an assertion fires, not merely that it passes

A check that has only ever passed cannot tell you it would catch a bad change. Limits exposes a package-private overload taking the limits as a record, so tests can exercise hypothetical sets and prove the assertion rejects them. Those tests pin the design's stated ceiling exactly — 332 meetings per day passes, 333 fails — and that caught a real contradiction: an early draft applied a blanket 2% safety margin, which would have quietly made the design's own published figure false.

The safety margin is asymmetric, on purpose

The item bound uses the raw 400 KB cap with no margin, because layer three measures the real serialised item before PutItem — the guarantee rests on measurement, so an optimistic model can only cause a premature "day is full", never an oversized item. The response bound carries a 2% margin, because nothing measures the real response at run time; there the model is the guarantee. A safety margin is not a ritual: ask what actually enforces the bound.

04 · Slice three

One query, and a cache that lies quietly

Four root fields collapsed into workspace(dates:). A page load is now one request, one invocation and one SnapStart restore instead of four of each, and the myPerson → meetings waterfall is gone entirely because the caller's identity arrives on the token.

The client side is three Apollo policies. None of them fails loudly when wrong, which is why each one carries its reasoning in the source: 

export const cache = new InMemoryCache({
  typePolicies: {
    // Day has no id. Keyed by date, so "empty day" and "unfetched day"
    // stay distinguishable — entity present with an empty list vs absent.
    Day: { keyFields: ['date'] },

    Workspace: {
      keyFields: false,                // a singleton, stored inline
      fields: { days: { merge: false } }  // replace, never accumulate
    },

    // ONE workspace slot, not one per dates array.
    Query: { fields: { workspace: { keyArgs: false } } },
  },
})
Silent · 3

Omit keyArgs: false and every distinct dates array gets its own ROOT_QUERY entry, with the same rooms and people cached again under each. It typechecks perfectly and no test notices. The only symptom is an app that refetches everything whenever the user changes week.

Three design claims that did not survive contact

All three were about the Apollo cache. That is worth naming as a pattern rather than three separate embarrassments:

Cache behaviour is the part of a design most likely to be wrong, because it is the part you cannot check by reading.

1. The days read policy was not implementable

The design specified a read policy mapping args.dates onto constructed Day references. But dates is an argument of workspace, not of days — a field policy on days receives no arguments at all. Reported rather than fudged; merge: false achieves what it was chosen for.

2. Returning a collection does not add to a cached list

The schema says returning the whole rooms collection "makes the mutation self-sufficient". It does not. Apollo normalises Room by id, so a created room is stored — but CreateRoomResult.rooms and Workspace.rooms are different cache fields, and nothing tells Apollo they are the same list.

Silent · 4

Settings showed the new room, because it renders straight from the mutation result. Add Meeting's cache-first dropdown did not, because it served the list it loaded with. No error anywhere. Caught by two acceptance tests that create something and then try to pick it.

3. Eviction does not leave a gap to fetch

Covered in full under real-time below, because that is where it bit — but it belongs to this list. Measured, not reasoned about.

TypeScript enforced the projection

Day-embedded meetings carry room { id } only; meeting details carries names. The compiler refusing Property 'name' does not exist on type '{ id: string; }' is the id-only projection being checked rather than merely intended.

The mocking approach had to match: fixtures hold the full shape, like stored data, and each mocked query projects what it selected. Storing the narrow shape left the mock unable to answer the wide query at all.

The race that only became reachable because the cache got faster

The captured DOM from a failed acceptance run showed both of these at once: 

- alert: "Please select an organiser."
- combobox "Organiser": Demo Strater

The banner says the organiser is missing; the field shows it. Not a contradiction — a sequence. The form was submitted while organiserId was still '', the server rejected it with OrganiserRequired, and the field filled in a moment later.

Silent · 8

Add Meeting gated rendering on the reference-data query. But the Organiser default comes from the signed-in user's own Person, which arrives from a different query (SESSION, in AuthProvider). Two independent loads, one gate — so the form was interactive, and submittable, while Organiser was still blank.

The part worth carrying to your own work: this was latent for as long as reference data was slow. Every visit used to pay a round trip for rooms and people, reliably slower than SESSION, so the person always won the race and the gap never opened. Serving reference data from the cache — the entire point of this design — makes a second visit render instantly and reverses the order.

A caching change does not just make things faster. It re-orders every race the old latency was accidentally serialising. None of those races are new; they were simply unreachable before.

It also explains failures that never mentioned it. When personId lands, setOrganiserId fires, filterAttendeeOptions(people, organiserId) returns a new array, and MUI rebuilds the open listbox — which is exactly element was detached from the DOM, retrying. A test clicking an option at that instant loses it. Two failures that never mentioned an organiser, plus the one that did — one cause. Both of the silent two pass in isolation, which is why they had gone unattributed: the race needs reference data to be already cached, and an isolated run starts empty.

Found by reading the failure's captured page state, not its assertion message. The assertion said expected URL /rooms/…/availability. Nothing in it mentioned an organiser.

05 · Slice four

Retention, and a deletion nobody could observe

A weekly job advances a stored Monday-aligned boundary and deletes the days behind it. The order of those two steps is the whole design, and it holds even if the job dies between them:

  • Delete first and there is a window where the boundary promises data that is already gone. Clients render empty days indistinguishable from "nothing was booked" — a silent lie.
  • Advance first and the opposite window opens: data exists but is not advertised. Harmless.

Any order works when everything succeeds. That is exactly why the failure case is what picks one.

Catch-up is free rather than special-cased, because the target is computed from today (Monday(today − 30)) rather than from the stored value — a job that missed three weeks lands in the right place on its next run. And deleteDaysBefore is strictly before: the boundary is the earliest date kept, not the first one removed. That off-by-one is the difference between honouring the retention promise and breaking it by a day.

The bug that needed two correct decisions to appear

The acceptance test could not observe a deletion at all, and neither decision responsible for that is wrong on its own:

  • Writes are bounded at the boundary (slice two), so a test cannot seed a day behind it.
  • The boundary is Monday(today − 30), so it only moves when the calendar does.

Together, a deletion is unobservable from outside. On the day this was written the target boundary equalled the stored one exactly — a real run was correctly a no-op, and the test was correctly red. The design's own suggested approach assumed each run advances a week. It does not.

The lesson is which seam, not whether to have one

Overriding the boundary would have been trivial — and would have bypassed the boundary computation, the single piece of logic most likely to be wrong. Overriding today leaves the job computing its own boundary from the supplied date, so the logic under test still runs and only the calendar is pinned. Absent, it uses the real clock, so the weekly schedule cannot be steered by an unexpected payload — which is why EventBridge sends {} explicitly.

A test seam in production code is a visible, argued decision recorded as an issue, rather than something a future reader finds and deletes as debug scaffolding.

Two ways this slice nearly created what it exists to remove

The retention job's whole purpose is to stop data accumulating forever. It came close to shipping two unbounded things of its own, in the infrastructure rather than the code.

A boundary that walks backwards, silently

The stored boundary is seeded by Terraform. Using timestamp() re-evaluates it on every plan, so the item drifts and every apply rewrites it; time_static captures it once at creation and keeps it in state. But ignore_changes is still required, and for a different reason than tidiness — the cleanup job advances that boundary at runtime, so without it the next apply resets it to the seed and walks the boundary backwards, re-advertising history that has already been deleted. Only on whichever apply happens to follow a cleanup run, and with nothing in the plan output to suggest anything is wrong.

Monday alignment had to be done in HCL, which has no weekday function. 1970-01-01 was a Thursday, so (days_since_epoch + 3) % 7 == 0 lands exactly on Mondays — checked against Python before deploying, because getting it wrong is silent too.

A log group with no expiry

logs.tf enumerates its functions explicitly. Miss an entry and Lambda auto-creates the group on first invocation with never-expire retention — the retention slice shipping precisely the unbounded artefact it was written to eliminate.

Both share a shape worth naming: the thing that accumulates is not always the thing you are thinking about. The design reasoned carefully about day items and said nothing about log groups, because log groups are not data.

Tests assert what survives

A job that deletes too much passes a test that only checks the old data is gone. So the assertions cover the days that must remain as carefully as the day that must go.

History is seeded through the API, not written into DynamoDB directly, so seeded days go through the real write path — the version-conditional write, the byte measurement, the pointer transaction. There is exactly one implementation of the day-item format and the test proves it rather than duplicating it. The cost is recorded in the test's own javadoc: past bookings must stay permanently legal, and a future rule rejecting them would break this test three files from the symptom.

Duplication that is deliberate

verify/ has no dependency on impl/, so RETENTION_DAYS = 30 is restated in the test rather than imported from Limits. That is the point: a shared constant would let the promise and the check drift together silently. Restated, a disagreement fails the acceptance run — which is the entire job of that suite.

06 · Slice five

Real-time, and finding out what AWS will not tell you

Before writing any subscription code, this slice stood up a throwaway AppSync API with the same auth pairing as production and interrogated it. Cost: about an hour, deleted afterwards. Six documented behaviours instead of six assumptions.

The probe had no install step at all — Node 24's built-in WebSocket global (no ws package) and SigV4 hand-rolled over node:crypto (no AWS SDK), about sixty lines. The precedent was selectionSetList, which was found missing by accident; this time the same instinct was applied on purpose.

The transport is AWS's own, not the one every library speaks

AppSync refuses the graphql-transport-ws subprotocol outright, which rules out Apollo's GraphQLWsLink and everything built on it. Its protocol is negotiated as graphql-ws but is a different message format entirely — ka not ping, start/data not subscribe/next:

One diagnostic line is the whole finding when probing: after the socket opens, ws.protocol tells you what the server actually negotiated. An empty string means it refused your subprotocol.

Almost every subscription failure is silent

Four of the six probed behaviours are cases where the publisher receives a clean success and the subscriber simply never receives anything. Exactly one failure is loud — and it is the one the design was most worried would be silent:

BehaviourWhat actually happens
Subscription type ≠ mutation return type Loud, at deploy. The subscription has an invalid output type.
Missing type-level auth directives Subscribe returns start_ack, then delivers nothing forever
Payload over the 240 KB cap Publish returns success; delivery does not happen
Unsupported filter field or operator Matches everything, or nothing — never an error
A rejected mutation Broadcasts exactly like a successful one
default_action = DENY with extra auth providers Refused outright — ALLOW is the only legal value
Silent · 5

The missing-directive case is the nastiest of these. The only symptom is Not Authorized to access dates on type Invalidation on the publisher's response — which in production is a Lambda nobody is watching. That is why the publisher inspects a 200 body for errors rather than trusting the status code.

Filters mislead rather than fail

The best teaching example of the whole exercise. Same publish, same API, four filters:

FilterResult
ok eq true — top-level scalarCorrect
meeting.id eq "m-1" — nested pathCorrect; nested paths do work
meeting.id beginsWith "m-"Matched nothing — dropped the success too
errors notContains "…" — list fieldMatched everything — delivered the reject

The same path with eq and with beginsWith gave opposite results, so it is the operator, not the path. Two unsupported combinations failed in opposite directions, and neither raised an error.

A test that only asserts "the message I wanted arrived" passes against a filter that matches everything. Assert both arrival and exclusion — one-sided assertions are how silent configuration bugs survive a green suite.

How the payload cap got answered properly

Not "is 217 days comfortably under 240 KB?" — obviously yes — but bracketing the real boundary, which is what establishes that the cap is size-based rather than count-based and that the published figure is accurate:

A question that dissolved instead of being answered

"Does AppSync enforce a 24-hour maximum connection lifetime?" is untestable inside a working session. But a subscription cannot outlive its connection, and there is no replay — a publish made while nobody was connected was lost outright. So the client must resubscribe and refetch on reconnect regardless of what the maximum turns out to be. The answer stopped mattering.

Worth adopting as a habit: before working hard on a question, check whether any answer changes the design.

Why the broadcast is a separate mutation

AppSync has no server-side publish API — a broadcast is a mutation call. So after a write commits, the resolver Lambda calls the API's own publishDaysInvalidated over IAM-signed HTTP. It exists as its own field because subscribing to createMeeting directly would broadcast rejected bookings, which return successfully with a typed errors array.

Two details make the permission a boundary rather than a label. The field is @aws_iam-only, so AppSync refuses a signed-in user's call before any resolver runs. And the Lambda's appsync:GraphQL grant names that single field rather than the API — apis/<id>/* would let it call every mutation as an IAM principal, bypassing the admin checks other resolvers perform.

A failed broadcast is logged and swallowed. The write has already committed and been reported to the caller, so failing the mutation would turn a missed optimisation into a lost booking — at the exact moment AppSync is unhealthy.

The client is not an Apollo link

GraphQLWsLink was ruled out by the subprotocol, but the deeper reason is worth stating to anyone who reaches for the framework abstraction by reflex: the broadcast carries dates, nothing renders it, and no component calls useSubscription. Routing it through Apollo's subscription machinery would buy link ordering and a lifecycle to manage in exchange for nothing. A small module that owns a socket and calls cache.evict is the right size.

One detail that looks pedantic and is not: eviction goes through cache.identify rather than a hand-built Day:{"date":…} string. Hardcoding the key format would turn a future cache-key change into an eviction that quietly stops matching. Nothing would throw; the app would just go stale.

Three hazards that are invisible until named

None of these would be found by writing the obvious code. They are the clearest argument in this body of work for designing before building:

  1. The booking tab is also a subscriber. Its own broadcast evicts the Day its own mutation response authoritatively wrote, so it re-renders empty while refetching — the person who made the booking watches their own screen flicker, on every create. The fix records the dates this client wrote and ignores invalidations for them briefly. The cost is written down rather than hidden: someone else's change to the same date inside that window is ignored too.
  2. An in-flight fetch can race an invalidation. A writes at t0; B's fetch was issued at t−1 and lands at t+1 carrying pre-write data, after B evicted at t0. B then holds stale data with nothing left to trigger another refetch — stale indefinitely, on one machine, with no error anywhere. A per-date "last invalidated at" marker, compared against the response's issue time, closes it.
  3. A gap in the connection is a gap in knowledge. There is no replay, so a reconnect or a return to the foreground evicts everything held rather than working out what was missed. Note this deliberately ignores the guard from hazard one: while the socket was down, a date this client wrote may also have been changed by someone else.

The one that only an acceptance test could catch

The design says the client "evicts Day:<date> and its ordinary gap fetch refills it". It does not. Measured, immediately after evicting a watched day: 

cache.diff(...) → complete: true, result: { workspace: { days: [] } }

workspace.days still holds a reference to the evicted Day, and Apollo filters dangling references out of a list on read. So the query reads back complete with one fewer day, not incomplete — there is no gap, nothing refetches, and the screen shows "no meetings" indefinitely.

Silent · 6

Every unit test passed. They asserted that the eviction happened — and it did. The defect lived in what eviction means to a watching query, which only a real browser watching a real screen could see.

The fix refetches active queries after an eviction that actually removed something. The test that pins the Apollo behaviour says so explicitly: if a future version makes that read incomplete, the test fails and the refetch should be deleted — which turns belt-and-braces into a dated claim rather than folklore.

07 · Shipping it

What the design only claimed until it was run

Everything above was written while the work was still on branches. It shipped as v2.0.0 on 11 September 2026, and the shipping turned out to have its own lessons — including two more entries for the index below, both in code written to fix what the release exposed.

The rebuild worked first time

This design chose destroy and rebuild both environments over any migration: every table, every Cognito user pool, every user. The Rollout section called that "a rehearsed operation, not a novel one", which was true but weaker than it sounded — the precedent had rebuilt environments the pipeline itself created. This time both were torn down by hand first, so the rebuild started from genuinely empty state files.

One run, no manual intervention, no retry. That settles a claim the design had been asserting rather than demonstrating: test and production are reproducible from the pipeline alone.

The predicted failure did not fire. A Cognito user pool domain is globally unique and released asynchronously, so recreating one immediately can fail; roughly four hours had passed and it was free. That does not bound the risk. One run showing four hours was enough says nothing about whether one hour would be, so the entry stayed in the Risks table rather than being quietly retired — writing "it was fine" would have converted a real risk into a false reassurance.

The deployment was green and the demo was empty

The release pipeline declines to seed production, and the comment explaining why is a good piece of reasoning:

demo-data already runs there daily on its own EventBridge schedule, and its concerns are idempotent — so a release does not need to force a run, and forcing one would be a write to production that the release does not need to make.

That holds for a normal release and fails for a rebuild, because after a destroy there is nothing for idempotence to be idempotent over. Production came up with 10 rooms' worth of schema and zero rooms of content, and stayed that way for about three hours until the 06:00 UTC schedule fired.

Silent · 11

The release reported complete success over an empty production. Nothing in the pipeline distinguishes a correctly rebuilt environment from an empty one — because the smoke suite asserts that headings render, and a heading renders perfectly well above an empty list.

A test that could not fail for the reason it existed

Looking at why the smoke passed produced the purest example in this entire document. The production test named meeting data reads back from the database and displays, in full: 

test('meeting data reads back from the database and displays', async ({ page }) => {
  await signIn(page)

  // Demo data is always deployed to production and refreshed daily, so production genuinely
  // has meetings to read. An empty page here means either the read path is broken or
  // demo-data has stopped running - both worth failing a release for.
  await page.getByRole('link', { name: 'Calendar', exact: true }).click()
})
Silent · 12

There is no assertion. The comment describes the failure it exists to catch, at length, and then nothing checks for it — the test passes if a nav link exists. It gates the automatic production rollback, so the rollback could not fire for the case the test was written for.

The fix was not the obvious one. Asserting that a meeting is visible would have been wrong: that page filters to a single person, and the seeder guaranteed a meeting on every weekday without guaranteeing the demo user was on any of them. The assertion would have failed for a data reason while looking like a broken read — and triggered a rollback that cannot repair a data problem. Making it deterministic had to come first.

v2.1.0, and being wrong in writing

So the seeder gained a fourth concern: a configured list of people who must have at least one meeting on every work day. The issue justifying it claimed the demo account got meetings at "roughly 1-in-40 odds per slot".

Measured on a real environment, natural coverage was 34 of 35 work days. Meetings carry many attendees, so a person lands on nearly every day by chance — the risk was real but far rarer than the justification said, and the smoke assertion would have been reliable without the feature at all. The issue was amended rather than left standing, because the next reader inherits the reasoning, not just the code.

The feature still earns its place on a narrower argument: a production gate should not depend on chance. But that is a different sentence from the one that opened the issue.

Silent · 13

The seeder's summary record gained a field and the Lambda's response did not, because the handler hand-builds its reply as an explicit map rather than serialising the record. It compiled, and 56 unit tests passed, with the new field invisible to every caller.

Silent · 14

Placing each guaranteed meeting checked that the room was free and never that the people were, double-booking whoever it invited. A local acceptance run passed with the defect present — it creates only three meetings, so whether any collides is luck. CI seeded differently and caught it.

One green acceptance run is not proof when the failure is probabilistic.

The path ephemeral environments cannot test

Shipping v2.1.0 did something the whole build had never done. Every environment until then — every ephemeral one, and both standing ones after the rebuild — was created. v2.1.0 modified two live environments instead: 

Plan: 1 to add, 8 to change, 0 to destroy
  # aws_ssm_parameter.demo_data_guaranteed_person_ids  will be created
  # aws_lambda_function.resolvers                      will be updated in-place
  // ... seven more, in place

Apply complete! Resources: 1 added, 7 changed, 0 destroyed

Ephemeral environments structurally cannot catch a permission needed only to modify an existing resource, or a state migration, or an in-place replacement — they only ever create. This was the first genuine exercise of that path, and nothing was replaced, so the Cognito attributes that ignore_changes protects were never touched.

07 · Throughout

Verification discipline

This is the part with the widest transfer outside mootmaker, and it is all one idea.

A green check is only as good as knowing what it checked.

Concretely, this is what the discipline was worth on the acceptance suite alone. Every number below came from a full run against a real deployed environment, with retries switched off:

PassedFailedWhat the fix turned out to be
9713starting point
1019five calls to root fields the composite query deleted — one of which had been passing while asserting nothing
1046a form submittable before its data loaded, and an assertion that waited on a condition already true
1100a fixture that had existed only by accident, restored deliberately

Not one of those four was what its failure message said it was. That is the whole section in a sentence: the failures that cost the most were the ones whose symptom pointed somewhere else entirely, and the only way through each one was to stop reading the assertion and start reading what the system actually did.

Real catches, in order of how ordinary they look

  • Incremental compilation masked a missing field. mvn compile reported BUILD SUCCESS while a handler referenced a field that did not exist. mvn clean compile failed immediately. For a refactor, incremental is not evidence.
  • Reordering same-typed positional parameters is invisible. Changing (client, rooms, people, meetings) to (client, meetings, rooms, people) compiled perfectly. Eighteen tests failed with No CONFIG#retention item in Rooms — and only because the error message happened to name the table.
  • An exit code is not a result. Read the surefire/failsafe XML per class, and check the report timestamps: it is entirely possible to read a green report from the night before while today's run never happened.
  • Do not pipe a run you intend to audit. ./verify.sh … | tail -40 makes the shell report tail's exit code, not the suite's — and truncates the very evidence you were about to read.
  • A least-privilege role is a test. Adding a write to a component that was only ever meant to delete failed with AccessDenied on dynamodb:PutItem. A role granting dynamodb:* would have accepted it silently.

The test that was green and asserting nothing

Found last, and only by grepping for siblings of a bug already fixed rather than fixing what the error messages named. An authorization test — it exists to prove a standard user cannot create a room — spot-checked its work like this: 

const roomNames = (afterBody.data?.rooms ?? []).map((r) => r.name)
expect(roomNames).not.toContain(`L90 Room ${runId}`)
Silent · 7

Query.rooms had been deleted, so data came back null, roomNames was [], and "does not contain the room that should not have been created" was trivially true. The defensive ?? [] turned a hard failure into a green tick. It never appeared in any failure list, because a vacuous pass is indistinguishable from a pass.

This is the same shape as the fake that ignored condition expressions, and it is worth putting next to it: a nullish-coalescing default on a value you are about to assert about will convert a broken query into a passing test. The fix is to fail loudly when the query itself does not resolve, which is the assertion the test always meant to make.

Fixture realism is part of the assertion

A day-limit test failed at 458,610 bytes against a 409,600 cap, which looked exactly like a wrong byte model. The model was right — the test's meeting ids were 41–45 characters instead of 36-character UUIDs. Exactly 200 extra bytes × 320 meetings accounted for the entire gap. A test that measures a system nobody runs will fail against limits that are correct.

Three failures that were all "when does this test run?"

Each blamed something else on the surface, and the last looked exactly like a real-time defect:

  • A unit test dated 2027-11-23 — beyond the 180-day booking horizon, correctly rejected.
  • Acceptance dates hardcoded behind a retention boundary that had since moved.
  • A test that booked 20:00–21:00 because it ran at 19:50. The meeting was created successfully; the availability grid renders only 08:00–17:00, so it fell off the visible screen.

A date in a test is a claim about when the test runs. Either pin the clock or derive the date from now() — and watch for "now" leaking in implicitly through a form default, which is how the third one happened.

That advice was eventually taken across the whole suite, and taking it broke something. See The same shape, from the other direction below.

Diffing two test runs, when a test's name contains its line number

Before the fixes: 13 failed, 97 passed. After: 9 failed, 101 passed. Diffing the two failure lists to find out which four changed produced this: 

=== FIXED ===  add-meeting.spec.ts:507 › blank organiser …
=== NEW ===    add-meeting.spec.ts:512 › blank organiser …

The same test. Playwright identifies a test as file:line:col › title, and the fixes added five lines above it. Three of the “new” failures were three old ones with shifted line numbers — and three genuinely new failures were hiding behind them, in a list that read plausibly either way. The corrected tally was 7 fixed, 6 still blocked on one missing fixture, 3 new.

Diff by title, not by the identifier the runner prints. This failure mode is silent and self-consistent: a mis-paired diff produces a clean-looking answer, and both halves of the mistake corroborate each other.

Three new failures with one shape

Two Autocomplete option clicks timing out, and a scroll-position assertion reading two equal numbers: 

waiting for getByRole('option', { name: 'F53 Attendee 1 …' })
  - locator resolved to <li role="option" …>
  - attempting click action
  - element was detached from the DOM, retrying

expect(leftFadeBox.x).toBeLessThan(rightFadeBox.x)
Expected: < 335    Received: 335

Three different assertions, one cause: the page re-rendered underneath the test. scrollLeft only resets to zero if the scroll container remounts — which is the detail that ties the third failure to the other two, and the reason to read three unrelated-looking failures together rather than one at a time.

All three pass in isolation against a freshly reset environment. The tempting conclusion is “flaky, ignore”. The honest one is narrower: the cause is something the isolated run does not have. Here, two candidates that both scale with how far into the suite you are — accumulated fixture data (the failing click was on data-option-index="16") and elapsed time on a live subscription that refetches every active query when it reconnects. An isolated pass narrows the search; it does not close it.

An auto-retrying assertion that is already true waits for nothing

E.36 scrolls the availability grid to its right-hand end and checks that the scroll-fade hint has moved from the right edge to the left. It guarded the measurement like this: 

await gridPaper(page).evaluate((el) => { el.scrollLeft = el.scrollWidth })
await expect(fadeHint).toHaveCount(1)     // intended as "wait for the re-render"
const leftFadeBox = await fadeHint.boundingBox()
expect(leftFadeBox.x).toBeLessThan(rightFadeBox.x)

Expected: < 335    Received: 335

The guard is the bug. Exactly one hint is mounted whichever edge is faded, so toHaveCount(1) is already satisfied by the stale right-edge hint and returns immediately. The test then measures that hint and compares its x against itself.

Setting scrollLeft fires onScroll → setState → re-render, all asynchronous. The trace of a real failure shows 10ms between the scroll and the measurement. Usually the re-render wins, which is why it passed for months.

Playwright's auto-retrying assertions only wait while they are false. Picking one whose condition does not change across the transition you care about buys nothing — and it reads like a wait, which is worse than having no wait at all. The fix polls the hint's own position, the only form that waits for the thing under test; a genuine regression still fails, now by timeout rather than by comparing a number to itself.

The trace, not the error message, identified this. The message named two numbers. The trace named the 10ms.

The fixture that existed by accident

Six acceptance tests failed on “an account with no linked Person”. The obvious reading is a fixture nobody had built yet. The truth was the opposite: it had existed for months by accident, and had just been deliberately removed. From the API's own Terraform: 

# Created directly rather than through sign-up, so PostConfirmationCreatePersonHandler never
# runs and neither the Person nor this claim would otherwise exist. Until now the e2e user had
# no Person at all, which meant the identity the whole acceptance suite runs as exercised the
# "no linked Person" path rather than the one every real user takes.
"custom:personId" = local.e2e_person_id

That change was right, and important — the entire suite had been running as a degraded identity. But five of those six tests were the only coverage of the degraded path itself, and they were silently depending on the accident. Fixing the fixture deleted the coverage.

The tests did not break. Their premise stopped being true, which is a different thing, and which nothing in their names, their assertions or their failure messages could tell you.

Confirmed by reading the live user pool rather than the code — two minutes of aws cognito-idp list-users in place of an afternoon of theory. The resolution was an account that is personless on purpose, named so, and deliberately not created in production, where a personless account is not a fixture but a real person's broken login.

Why this one is worth the space

With the fixture restored, all six pass — first time, no drift. The behaviour had been untested for weeks and was fine, which is exactly the case that teaches people the coverage never mattered. It did. Six tests went red for a reason that had nothing to do with what they assert, and every cheap fix for that red — delete them, rewrite them, mark them skipped — also throws away the only checks on a real user-facing path, leaving no trace it existed.

A test failing for a reason unrelated to its subject is the most dangerous kind of red. Ask what a test is for before deciding what to do about its failure.

I verified the precondition. Then the suite destroyed it.

Five acceptance tests cover what an account with no linked Person sees. Their fixture had existed only by accident and was deliberately removed, so a replacement account was added, deployed, and checked directly rather than trusted from Apply complete!: 

no-person-tests@example.com   CONFIRMED   custom:class=standard   (no custom:personId)

Exactly right. The full run then failed all six tests that sign in as it: 

Incorrect username or password.

database-reset deletes every Cognito user whose email is not in RESERVED_ACCOUNT_EMAILS, and that list named the demo and e2e accounts literally. The suite resets the environment before it runs. So Terraform created the account, it was verified, the suite deleted it, and then signed in as it.

The verification was correct and worthless at the same time, which is a combination worth being able to name. A precondition check only means something relative to what happens between the check and the use — and here the pipeline itself was what invalidated it, seconds later, by design.

Two details make it harder than it sounds. The message named nothing useful: a deleted account and a wrong password are indistinguishable from outside. And no test of the program could have caught it — wipeCognitoPool takes the reserved set as a parameter and its unit tests pass one explicitly, so the Java was never wrong. The defect lived entirely in deployment wiring.

The habit

When you add a fixture, ask what else in the pipeline already has an opinion about it. A reset, a cleanup job, a retention sweep and a seeding script will all act on your new object without ever being told it exists.

The same shape, from the other direction

Fourteen tests pinned their clock to a hardcoded calendar date. That is a slow-burning bug: the retention boundary advances every Monday, and once it passes a pinned date every booking that test makes is rejected. Eight of them were due to break on a known Wednesday a fortnight out. Replacing the literals with dates derived from now() fixed that, and broke one test: 

G.63 - a day with three meetings lists them in ascending start-time order
Expected: 3    Received: 5

The literals had been scattered across five months. Not for any stated reason — each test simply picked a date — but the effect was that no two tests ever booked the same user onto the same day. Anchoring them to one week collapsed that spread, and G.63 is the only case in the suite that counts every row in a day cell rather than looking for its own subjects. It picked up two other tests' meetings.

Which is the personless account again, running the other way: a property nothing declared, which something depended on. There, a fixture that existed by accident was removed. Here, a separation that existed by accident was removed. Both broke a test that never mentioned the property.

So the fix is not “move G.63 somewhere quiet”. It is to write down that the isolation is load-bearing, and why eight weeks specifically: clear of the current-week fixtures behind it, and clear of the room-suggestion cases sixteen weeks ahead, since the calendar window is six weeks long and reaches neither.

What to expect from this kind of refactor

The change made the suite better and directly caused a failure. Both are true. Consolidating scattered values surfaces every accidental separation among them at once — so expect it, and read the failures as information about what the old scatter had been quietly providing.

The whole component nobody re-ran

Verifying the design's checklist against the code, rather than ticking it from memory, found that mootmaker-demo-data — one of the three deployable components — had been broken against the deployed schema for days. Not subtly, and not in one place:

  • Query.rooms, Query.people, Query.meetings — all three deleted by the composite entry point.
  • createPerson selecting { id name } off a result type that has never had those fields.
  • Its own acceptance suite calling the same deleted Query.meetings.
  • That suite's window computed from the local clock rather than the server's.

Each one was hidden behind the one before it. Nobody had re-run the component because nothing failed: its forty-five unit tests were green throughout, and stayed green through the first three fixes.

Silent · 10

FakeGraphQlClient returned id and name directly on createPerson's result — a shape the schema has never allowed. So the unit tests asserted against an API that does not exist, and passed, for as long as anyone cared to run them.

That is this tour's own line — a fake confirms your model of a dependency, not the dependency — arriving while writing new tests against that same fake. The fake also threw on any meetings operation, which is the right default and still did not help: those operations were never exercised at all, so nothing reached the guard.

One practical note from working through it: a run that gets further is progress, even while it still fails. Seeding time going 19s → 34s was the clearest evidence the first fix had landed, well before any test turned green.

The design's own rule, broken by the design's own test suite

demo-data's acceptance suite failed with a date and no explanation: 

business days with no meetings: [2026-10-22]

It computes its window from LocalDate.now() and asserts every business day in it got a meeting. The seeder runs in Lambda, in UTC. The suite runs on a workstation in New Zealand, up to thirteen hours ahead. Measured at the moment of failure: 

local: 2026-09-11 01:42 NZST   → wanted business days through 2026-10-22
UTC:   2026-09-10 13:42        → seeder filled them through 2026-10-21

One day apart, so the test demanded a day nothing had been asked to fill. The design already says this, about clients computing retention dates:

Having the client work out "30 days before today" puts two authorities on one fact: the deletion job uses the server's date, the browser uses the user's.

Same trap, in a test rather than the app — and the design even predicted why it survives: "a test would not catch it because the test would encode the same assumption the code does."

The shape is worth recognising on sight: it fails only for part of each day. In UTC it never fails. In New Zealand small hours it always does. A bug with that shape is invisible to whoever wrote it and unmissable to someone twelve hours away. And the message names a date, not a clock, which is the expensive part.

The fix is the one the design prescribes: ask the authority that owns the fact. The API publishes latestBookableDate as server-today plus the horizon, so subtracting the horizon recovers the server's own date. No second opinion exists to disagree with.

A limit that reported itself as a null

Asking workspace for 51 dates, against a cap of 42, returned this and nothing else: 

Cannot return null for non-nullable type: 'Workspace' within parent 'Query'

The handler throws Too many dates requested: 51 exceeds the limit of 42. — a message naming both numbers. It never reached the client. The direct-Lambda response template was $util.toJson($ctx.result) with no $ctx.error branch, so a thrown handler produced a null result and AppSync's nullability complaint was the only error returned.

Silent · 9

Every server-side limit, bad request and internal fault in the entire API arrived as that one sentence, which names the schema rather than the problem. Ordinary validation was never affected — MeetingError and friends are typed errors arrays returned normally, not exceptions — so the common path looked fine while the diagnostic path was mute. Exactly backwards from where you need detail.

No unit test could have caught it. The handler's own tests prove it throws the right message, and they passed throughout. What was broken was the wiring between handler and client, which exists only in a deployment.

Documentation that argues for the opposite of what is now true

Sweeping every markdown file in the workspace for the deleted root fields found four documents wrong — and how they were wrong matters more than the fact of it. They had not gone vague. They made confident, reasoned cases for the architecture that had just been removed.

The webapp README explained why the three pages cannot share a cache entry:

Apollo's cache keys a list field by its exact arguments, so a narrower window (e.g. HomePage's 2 days) isn't served from a broader cached one (e.g. PersonCalendarPage's 6 weeks) even when it's a subset.

Entirely correct when written. Sharing that cache is the whole point of the change that landed — days are entities keyed by date, so one Day serves every page that asks. The document was still arguing for why that was impossible.

The API README described three id-keyed tables, four GSI access patterns and a join table, each with its reasoning, and linked to MyPersonHandler.java — a file that no longer exists. And data-model.md, titled "Domain data model — current state", described the previous one; the design had even enumerated the exact delta it needed, and nobody had applied it.

Why detail makes this worse, not better

A vague document gets checked against the code. A document that explains why, with trade-offs and measured numbers, earns exactly the trust that stops you checking. These were the good kind of documentation, which is what made them expensive: a reader arriving at this codebase would have believed them over the source for at least an hour.

Not all old references are drift

Two documents kept their references to deleted fields, deliberately. A design record opens with "Status: implemented … kept as the design record for why and how, written at proposal time" — its field list is what the schema held when it was written. An incident table records a Playwright timeout where two notices "rendered while myPerson was in flight"; that is what happened, and renaming the query would falsify the record.

The distinction is whether the document claims to describe the present. “Current state” in a title is a promise. “Written at proposal time” is a date stamp. Only the first kind can rot — and a sweep that edits the second kind is destroying evidence, not fixing drift.

Two of these had one cause, and it is structural

An authorization test that asserted nothing (7) and a component broken for days behind green unit tests (10) look unrelated. They are the same hole: nothing validates hand-written GraphQL that codegen never sees.

Operations live inChecked byResult
the webapp's src/codegen:check, every PR, offlineNever broke
the webapp's acceptance/nothingSix dead calls; one of them silent
demo-datanothing (a hand-written fake)Four breakages, green CI throughout
the API's verify/runs against a real deploymentFails loudly, but only when run

The guarded column is not more careful than the others. It is guarded — regenerate from the published schema, fail if the output differs, no environment required. Every place without that line in CI drifted, and the drift was invisible until something happened to exercise it.

Worth being precise about the failure mode, because "it would have broken" undersells it. An unguarded operation does not merely stop working: (body.data?.rooms ?? []) turned a deleted field into an empty list, and an assertion about what a standard user must not be able to do became trivially true. The absence of a schema check converted a security test into a no-op, and left it green.

A command that never ran looks exactly like one that failed

The final gate before handing this work over was the API's unit suite. It reported: 

API TEST EXIT=1

Which is a build failure, at the last possible moment — except the surefire reports told a different story. All twenty-five of them were fifteen minutes stale. Nothing had run. The command was a compound cd && mvn, the working directory had been moved by an earlier background task, the cd failed, and the chain short-circuited before Maven was ever invoked.

The exit code was real. It just measured something other than what it appeared to. A command that never ran and a command that failed are indistinguishable from an exit code alone — and the second is far less alarming than the first, because a failure you can read is a failure you can fix, while a run that did not happen leaves you believing you tested something you did not.

This is the whole reason the discipline is read the reports and check their timestamps, rather than either alone. Report contents would have said 202 passed, 0 failed — from the previous run, perfectly reassuring and completely irrelevant. Only the mtime distinguishes fresh evidence from a stale artifact that happens to say what you hoped.

Re-run with an absolute path: 202 tests, 0 failures, reports written seconds ago. The fix is boring; noticing that it was needed is not.

Duplication that exists so two things can disagree

The acceptance suite restates the retention window as its own constant rather than importing Limits.RETENTION_DAYS_MINIMUM. verify/ deliberately has no dependency on impl/, and the duplication is the point:

A shared constant would let the promise and the check drift together, silently.

Import the value and the test asks "does the code agree with itself?", which it always will. Restate it, and the two can disagree — which is the only condition under which the acceptance run has anything to say. If someone changes the retention minimum without meaning to, the suite fails; that is its entire job.

Worth pairing with its opposite. Limits.assertConsistent() runs inside the deployed artefact, at SnapStart init, and there the instinct inverts: everything is imported, because the whole purpose is to check that one set of numbers is internally coherent before a version is published. Same goal — make disagreement loud — opposite side of the boundary, opposite technique.

The general rule this suggests: share a constant when you want two things to move together; restate it when the point is to notice that they didn't. "Don't repeat yourself" answers the first case and quietly sabotages the second.

Proving that something does not happen

Both suites needed a dedicated concept for it — receivedNothingWithin(Duration) in Java, an explicit wait before toHaveCount(0) in Playwright. There is no event to poll for, so the only honest approach is to wait and confirm nothing turned up. That wait always expires in full, so it is a real cost paid on every run, which is why it is deliberately shorter than the positive-path timeout.

Related, and easy to mistake for flakiness: awaitReady() before publishing is not defensive padding. Publishing between start and start_ack genuinely loses the broadcast, and without the wait the test fails intermittently for a reason that has nothing to do with the code under test.

08 · Closing

The silent-failure index

Fourteen things in this tour are marked as silent. They are not fourteen unrelated bugs — they are the same bug wearing different clothes, and collecting them is the most useful thing this document does. The seventh was found only because the sixth prompted a search for its siblings. The eighth was found by reading a failure's captured page state instead of its error message. Two were found by a component nobody had re-run since the schema changed under it.

The last four arrived after shipping, and three of them are worse than the first ten in one specific way: 11 and 12 were found by looking at a release that had just reported success, and 13 and 14 are in code written to fix them. Nothing about knowing this failure mode well made the next one easier to see.

#What looked fineWhat was actually true
1A resolver returned a 200An aliased field nulled a whole meeting
2Optimistic-locking tests passedThe fake ignored condition expressions entirely

The common shape: the check that ran was not the check that mattered. A compiler confirms types, not intent. A fake confirms your model of a dependency, not the dependency. A unit test confirms an action happened, not what that action means to everything watching. Each of these needed a check at a different layer — and in three cases, the only layer that could see it was a real deployment.

If you take one habit from this

When something passes, ask what would have to be broken for it still to pass. If the answer is "quite a lot", the check is doing less than it appears to. That question is what produced the inverted selection test, the fake that throws on unmodelled conditions, the assertion tested by making it fire, and every two-sided broadcast assertion in the real-time suite.

And when you find one, look for its siblings before moving on. Six of these were found by something failing. The seventh was found by going looking — and it was the one that had been quietly wrong the longest. The eighth came from a habit worth stating separately: when a test fails, read the state it captured, not only the sentence it printed. That failure's message named a URL. Its snapshot named the bug.

This document was audited against the code it describes. Every identifier it names was grepped against the three repositories, every quoted snippet and blockquote diffed against its source, and every figure recomputed — 400 KB as 409,600, 240 KiB as 245,760, the 217-day table bound as 180 + 36 + 1.

It found two errors, and where they were is the useful part. Every measured number survived. Both errors were in prose recalling code structure: a test double named FakeDayTable, which has never existed — the real change extended FakeDynamoDbClient in place, which is the better story — and a method signature given as void that returns Day. Measured claims held; remembered ones did not. Both sat in the oldest sections, written first and re-read most, which is exactly where familiarity stops you looking.
