# DynamoDB storage compaction

## Summary

Shrink the persisted byte footprint of a meeting so the day item's 400 KB DynamoDB cap stops being
the thing that limits `MAX_MEETINGS_PER_DAY` and `MAX_ATTENDEES_PER_MEETING`, and so there is real
headroom for the upcoming per-attendee response-status field (coming/not coming/tentative/no
response) without shrinking either limit further. Two changes, both confined to the small
model/dynamo layer in `mootmaker-api` that already owns DynamoDB item (de)serialization: (1) encode
`startTime`/`endTime` as a compact number instead of a 19-byte ISO string, and (2) replace 36-byte
UUID ids with a short opaque token, generated by one small allocator instead of five scattered
`UUID.randomUUID()` call sites. Both are pure encoding changes — GraphQL contracts, the webapp,
and demo-data see no difference, because ids and times already cross that boundary as opaque
strings.

## Status

**Drafting** — 2026-09-20.

## Scope / non-goals

In scope:

- Compact encoding for `startTime`/`endTime` on a persisted `MeetingRecord`.
- A compact id scheme for `Meeting.id`, `Room.id`, `Person.id` (and therefore `roomId`,
  `organiserId`, `attendeeIds`, and the `PTR#` pointer key, all of which embed these ids), replacing
  `UUID.randomUUID().toString()`.
- Consolidating id generation into one small, reusable piece instead of six independent call sites.
- Recomputing `Limits`' byte model and raising `MAX_MEETINGS_PER_DAY` (and possibly
  `MAX_ATTENDEES_PER_MEETING`) now that the model has headroom, while reserving budget for the
  attendee-status field described below.
- Auditing every place outside `mootmaker-api` that could assume today's id/datetime shapes.

Non-goals:

- **Actually building the per-attendee response-status field.** That is a separate feature with its
  own GraphQL/webapp/UI work and deserves its own design doc. This doc only makes sure the storage
  budget has room for it — see "Reserved headroom" below — and sketches the cheapest persisted shape
  for it so the budget estimate is grounded in something real, not a guess.
- Any change to the `Meeting`/`MeetingInput` GraphQL contract, `Person`/`Room` GraphQL contracts, or
  anything the webapp/android/demo-data read over GraphQL. `id: ID!` stays an opaque string;
  `startTime`/`endTime` stay ISO-8601 local date-time strings in every response. This is an
  internal-storage-only change.
- A data migration for existing records. Per project convention, `test`/`production` data is
  disposable demo data — see "Rollout & migration".
- Changing the Rooms/People DynamoDB attribute *type* for `id` (staying `S`, not moving to `N`) —
  see "Trade-offs and decisions" for why.

## Trade-offs and decisions

- **Ids stay DynamoDB type `S` (string), Java type `String`, GraphQL type `ID!` — only the *value*
  gets shorter.** UUIDs are 36-byte string values; the fix is generating a shorter string, not
  switching the attribute to a DynamoDB number (`N`). A numeric type would save a further ~3 bytes
  per id occurrence (see the byte model below) but costs real blast radius: `BatchGet.byId` hardcodes
  `.s(id)` / `item.get("id").s()`, the Rooms/People tables' `hash_key` attribute type would have to
  change in Terraform (table replacement), and every response mapper would need an explicit
  `.toString()` at the GraphQL boundary that today happens for free. The 8-char vs 36-char move
  already captures the overwhelming majority of the win (see the model below); chasing the last ~15%
  by changing types everywhere is not worth it. This is exactly the kind of change the user's own ask
  wanted to *avoid* leaking outside the dynamo/model layer.
- **`startTime`/`endTime` become epoch-minutes-since-UTC, stored as `N`, not epoch millis.** The user
  suggested millis-since-UTC; minutes gets the same simplicity (`LocalDateTime.toEpochSecond` /
  `LocalDateTime.ofEpochSecond`, treating the naive local value as if it were UTC purely as an
  internal encoding convention — there is no real zone attached to these values today either, see
  `MeetingRecord`'s existing "LocalDateTime semantics" comment) with a smaller stored number, because
  every stored value already has `:00` seconds and falls on a 15-minute boundary (`MeetingInput`
  validation enforces this) — millisecond and second precision store information that never varies.
  Concretely: millis needs ~13 digits (~8 bytes as `N`); minutes needs ~8 digits (~5 bytes as `N`),
  for the same conversion complexity. This is a value-only change fully self-contained in
  `MeetingRecord.toAttributeValue`/`fromAttributeValue` — `date()` still derives from the decoded
  value the same way it does today, no other file touches this representation.
- **Id generation moves out of the five/six handlers that currently call
  `UUID.randomUUID().toString()` inline, into one small allocator in the `dynamo` package.** This is
  what the user asked for directly ("encapsulated within this same small layer that touches DynamoDB
  records"), and it also fixes a real inconsistency found while researching this: `CreatePersonHandler`
  writes a `Person` via a raw `dynamoDbClient.putItem(...)`, bypassing `PersonRepository` entirely,
  while `CreateRoomHandler`/`RoomRepository` and demo-data-facing paths are more consistent. Folding
  id allocation into the repositories is a chance to close that gap at the same time, not a separate
  piece of scope creep — the collision-retry logic (see below) has to live somewhere that already
  owns the write, and that's the repository, not the handler.
- **Collision-safety reuses conditional writes that mostly already exist, rather than adding a new
  uniqueness-checking structure.** See "Id allocation options" below — this directly answers "open to
  adding extra storage if needed": for meetings, the `PTR#` pointer write already happens inside
  `DayRepository`'s transaction, so a `condition_not_exists` on the pointer plus retrying the *whole*
  `mutate` attempt (which `DayRepository.mutate` already loops on `ConditionalCheckFailedException` /
  `TransactionCanceledException`, for the unrelated reason of version conflicts) gets collision
  retry for free if the id is generated freshly on each attempt rather than once before calling
  `mutate`. Rooms/People need a few new lines each (a `condition_not_exists(id)` on their `PutItem`
  plus a small bounded retry), mirroring `DayRepository.MAX_WRITE_ATTEMPTS`'s existing shape.
- **Decided: random token, base62 alphabet, 8 characters (Option A below) — 2026-09-20.** A
  Hi-Lo/segment block-allocation counter (refining Option B with the pattern behind Hibernate's
  `hilo` generator, Flickr's Ticket Servers, and Meituan Leaf's segment mode — one write reserves a
  *range* of ids, not one write per id) was researched as an alternative and would let ids be
  numeric with a small digit count at zero collision risk. It's a real, well-precedented option and
  worth revisiting if id-generation ever needs to scale past what a single conditional write can
  handle — but it adds a new stored item, a lazy-initialization requirement specific to this
  codebase's SnapStart-restored Lambda environments (a block reserved during Lambda *init* would be
  duplicated across every environment restored from that snapshot, so it must be reserved on first
  post-restore use, not at init), and a DatabaseReset.java touch point to decide whether the counter
  resets with everything else. The random-token option needs none of that: no new storage, no new
  lazy-init rule, and 8 base62 characters (~2.18×10^14 possible values) is far more entropy than this
  periodically-wiped demo system will ever approach, with the existing conditional-write retry as a
  correctness backstop rather than a probability anyone expects to be tested. Base62 (alphanumeric
  only) over base64url (which adds `-`/`_`) for the same reason ids were opaque strings in the first
  place — nothing about them needs to be copy/paste- or link-safe today, but there's no reason to
  give that up for a fractional entropy gain (64 vs 62 symbols) that doesn't matter at this scale.

## Changes to the domain data model and data storage models

Delta against [`../docs/reference/data-model.md`](../docs/reference/data-model.md):

- **Meetings table, `meetings` list, each element:** `id`, `roomId`, `organiserId`, each element of
  `attendeeIds` — same attribute names, DynamoDB type stays `S`, value goes from a 36-character UUID
  to an 8-character base62 (`A–Z a–z 0–9`) random token (**decided** — see "Trade-offs and
  decisions"). `startTime`/`endTime` — DynamoDB type changes from `S` (19-char fixed-width ISO
  string) to `N` (epoch-minutes-since-UTC, an internal encoding convention with no real timezone
  attached, exactly matching how these values already have no real timezone attached as naive
  `LocalDateTime`s).
- **Rooms table, People table:** `id` value goes from UUID to the same 8-character base62 token;
  attribute type stays `S`, so the tables' own schema (`hash_key = "id"`, type `S`) is unchanged.
- **Pointer items (`PTR#<meetingId>`):** unchanged shape; `<meetingId>` is just shorter now.
- Nothing about `CONFIG#retention` changes, and no new stored state is introduced — the random-token
  approach needs no counter item (see "Id allocation options" below).

## Technical considerations

### The byte model, before and after

Current constants (`Limits.java`), and what a worst-case day costs today:

| Quantity | Value |
|---|---|
| `PER_MEETING_BASE_BYTES` (id, roomId, organiserId, startTime, endTime, container overhead — excludes attendees/subject) | 212 |
| `BYTES_PER_ATTENDEE` (36-byte UUID + 1 list-element overhead) | 37 |
| `MAX_SUBJECT_BYTES` | 280 |
| `MAX_MEETINGS_PER_DAY` × `MAX_ATTENDEES_PER_MEETING` | 320 × 20 |
| **worst-case meeting** = 212 + 37×20 + 280 | **1,232 bytes** |
| **worst-case day item** = 320×1,232 + 128 (day overhead) | **394,368 bytes — 96.3% of the 400 KB cap** |

That 15,232 bytes of headroom is the whole problem: there is no room left to add anything, including
one byte per attendee.

Proposed changes, as per-value byte deltas (attribute names and container overhead are unchanged, so
only the value costs move):

| Field | Before (S) | After | Delta |
|---|---|---|---|
| `id` | 36 (UUID) | 8 (short token, S) | −28 |
| `roomId` | 36 | 8 | −28 |
| `organiserId` | 36 | 8 | −28 |
| `startTime` | 19 (ISO string, S) | ~5 (epoch-minutes, N) | −14 |
| `endTime` | 19 | ~5 | −14 |
| each `attendeeIds` element | 36 (+1 overhead = 37) | 8 (+1 overhead = 9) | −28 |
| **new** each `attendeeStatuses` element (reserved, not built here) | — | 1 byte code (+1 overhead = 2) | +2 |
| **new** `attendeeStatuses` list's own name + container overhead (one-time per meeting) | — | ~20 | +20 |

Recomputing the model with these deltas, at **today's limits — decided to stay unchanged, 320
meetings/day, 20 attendees/meeting, 280-byte subject** — **and** the attendee-status field's bytes
already reserved:

- `PER_MEETING_BASE_BYTES` ≈ 212 − 28×3 − 14×2 + 20 = **120**
- `BYTES_PER_ATTENDEE` (id + reserved status) ≈ 9 + 2 = **11**
- worst-case meeting = 120 + 11×20 + 280 = **620 bytes** (down from 1,232 — practically half, before
  even touching the limits)
- **worst-case day item at 320 meetings = 320×620 + 128 = 198,528 bytes — 48.5% of the cap.** This is
  the adopted result: `MAX_MEETINGS_PER_DAY` and `MAX_ATTENDEES_PER_MEETING` both stay as they are
  today (see "Open questions"), so this compaction work is pure safety margin and headroom for the
  attendee-status field, not a capacity increase.
- For the record, the alternative considered and not adopted: raising `MAX_MEETINGS_PER_DAY` to 360
  (true physical capacity — 10 rooms × 36 fifteen-minute slots) would have cost
  360×620 + 128 = **223,328 bytes — 54.5% of the cap**, still comfortably under the limit. Available
  as a follow-up later without touching anything else in this design.

Subject text (280 of 620 bytes, 45%) is now the largest single contributor to a meeting's size — the
next lever if more headroom is ever wanted, not proposed here.

These are estimates in the same spirit as today's `Limits.java` model, not exact — `ItemSizer`
already measures the real serialised item at write time and is the actual backstop
(`Limits.assertConsistent()` catches an inconsistent model at deploy time, before it reaches a user).
Implementation should recompute the constants precisely against `ItemSizer`'s actual rules rather
than trusting the arithmetic above to the byte.

### Id allocation options

Neither option changes anything a caller of `MeetingRecord`, `Person`, or `Room` sees — both produce
a short opaque string.

**Option A — random token. Decided, 2026-09-20: base62 alphabet, 8 characters.** Generate the token
`SecureRandom`-backed. No new stored state: collision safety reuses each entity's own uniqueness
check that already exists or is one line away —
- Room/Person: add `condition_not_exists(id)` to the existing `PutItem`; on
  `ConditionalCheckFailedException`, generate a fresh token and retry (bounded, a handful of
  attempts).
- Meeting: the `PTR#<id>` pointer is already written inside `DayRepository.mutate`'s transaction;
  give that `Put` a `condition_not_exists(pk)` and generate the meeting's id *inside* the
  `UnaryOperator<Day>` passed to `mutate` (rather than once, before calling it) — `mutate`'s existing
  retry-on-`TransactionCanceledException` loop then covers an id collision the same way it already
  covers a version conflict, with no new retry logic to write.
- Collision probability at this system's actual scale (a demo system, periodically wiped) is
  negligible even without the retry backstop — 8 base62 characters is 62⁸ ≈ 2.18×10^14 possible
  values — the retry loop exists as a correctness guarantee, not because a collision is expected to
  happen. (Base62 — `A–Z a–z 0–9`, no `-`/`_` — over the marginally larger base64url alphabet: the
  entropy difference at this length, 2.18×10^14 vs 2.81×10^14, doesn't matter at this scale, and
  alphanumeric-only avoids `-`/`_` occasionally being mangled by things that treat them as
  word-boundary punctuation, even though nothing about these ids needs to be link-safe today.)
- Ids are not sequential or guessable-by-count, which costs nothing here since nothing in this system
  relies on id-unguessability for authorization today (`MeetingByIdHandler` only checks
  `Identity.requireAuthenticated` — any signed-in user can already look up any meeting by id).

**Option B — sequential counter, not chosen.** One new tiny config item (e.g. `CONFIG#idCounters`,
following the existing `CONFIG#retention` pattern), incremented via DynamoDB's atomic
`UpdateItem ... ADD` — a true atomic increment, not a read-modify-write, so it needs no retry loop
and no contention concern even
under concurrent creates (unlike the Day item's optimistic-lock pattern, this is the pattern DynamoDB
atomic counters exist for). Encode the returned counter in base62 for compactness (4 chars covers 14.7M
values). No collision handling needed at all — uniqueness is by construction. Trade-off: ids reveal
creation order and approximate volume (low-stakes here, per the above), and it adds one new small
piece of stored state, which is exactly the "open to adding extra storage" the user offered as
acceptable if needed — here it plainly isn't *needed*, just an available alternative.

A refinement of Option B was also researched and rejected: **Hi-Lo / segment block-allocation** — the
pattern behind Hibernate's `hilo` id generator, Flickr's Ticket Servers, and Meituan Leaf's segment
mode (`leaf_alloc` table: `biz_tag`, `max_id`, `step`). Instead of one `ADD` per id, a caller reserves
a whole *block* of ids in one `ADD :step` and dispenses them from memory until exhausted — the same
idea as Option B's counter, but touching the counter item once per `step` ids instead of once per id.
It would let ids be numeric with a small digit count at zero collision risk (see the earlier byte
discussion on this doc's PR/thread). Not adopted because, on top of Option B's own trade-offs, it
needs a lazy-initialization rule specific to this codebase's SnapStart-restored Lambda environments —
a block reserved during Lambda *init* would be captured into the snapshot and handed out identically,
and duplicated, by every environment restored from it, so the block must be reserved on first
post-restore use, never at init — plus a `DatabaseReset.java` decision about whether the counter item
resets with everything else. Worth revisiting if id generation ever needs to scale past what a single
conditional write can handle; not needed at this system's actual write volume.

Recommendation, and decision: **Option A**, base62, 8 characters. It needs no new storage, no new
operational concept, and reuses mechanisms `DayRepository` already has for an unrelated reason.

### What this doesn't touch

- `ItemSizer` — already generic over whatever `AttributeValue` shapes it's given; needs no change.
- The GraphQL schema, `webapp/src/graphql/types.ts`, android — ids and times cross this boundary as
  opaque strings already (`Meeting.id: ID!`, `startTime: String!` in ISO form), so nothing here is
  visible to them. Verify this holds, rather than assuming it — see "Testing impacts".
- `mootmaker-demo-data` — creates meetings/people/rooms over GraphQL, not direct DynamoDB access, and
  doesn't generate ids itself.

## Rollout & migration

No migration needed. Per project convention (`test`/`production` hold disposable demo data,
regenerated by `mootmaker-demo-data`, and both environments change only through `release.yml`), this
ships as a normal release: old UUID-keyed / ISO-string-keyed items simply stop being written once the
new build is live, and existing items are wiped by the next `database-reset` rather than migrated in
place. `DatabaseReset.java` was checked and reads ids/keys generically (`item.get("id")`, whatever
`AttributeValue` type is present) — it has no hardcoded assumption about id shape or type to break
either way.

For an ephemeral dev environment: build, deploy, and reset/reseed with demo data — no special
handling.

## Risks

- **Byte-model drift.** Same risk that exists today, unchanged in kind: `Limits`' constants are an
  estimate, `ItemSizer` is the real backstop, and `Limits.assertConsistent()` fails a deploy loudly if
  they've drifted apart. This design doesn't weaken that guarantee, and actually gives it much more
  margin to work with (55% vs 96% utilization at the new limits).
- **Collision-retry code is new** and needs its own test coverage (see "Testing impacts") — a bug
  there (e.g. retrying without regenerating the id) would be a silent hang or a spurious rejection
  under the (currently negligible) chance of a real collision.
- **Reversibility**: this is easy to ship (no migration, no long-lived state to unwind) and easy to
  revert if something's wrong post-deploy, since — per project convention — the data is disposable
  either way.
